# Coordinated router configuration

Use one `glinet_uci_configuration` resource per router to manage network, wireless, DHCP, firewall, `gl-dns-v2`, and Ethernet port mapping together. Build the provider using the [development setup](development.md), then adapt the [synthetic example](../examples/resources/glinet_uci_configuration/resource.tf).

## Adopt existing settings

1. Read the router through a verified SSH connection and describe the desired managed sections using `jsonencode`. The provider requires the section type to match. Named sections are created if missing. Anonymous selectors such as `@zone[0]` select the unique section of that type; add `match = { name = "guest" }` when the type has multiple sections. Use `match` only with anonymous sections. The numeric selector is an identifier within the configuration; identity is resolved by type and the unique match rather than by mutable position.
2. Run `terraform plan` and inspect the configuration. Creating the Terraform resource adopts matching settings without commits, reloads, or reboot. Terraform identifiers and nonsecret settings are stored in state. Protect the local state directory and exclude it from version control.
3. Keep an external encrypted router backup and a verified management connection before applying. Do not overlap section ownership with other Terraform resources, the administration UI, or other tools.

Missing members remain drift within the coordinated resource and preserve its key-rotation generation. The `missing` marker is reserved for observed state. Only supported nonsecret options and lists are accepted and managed. Wi-Fi attributes use scalar options. Other option names, including WEP key slots, are rejected. Omitted settings remain unchanged. Remove a named section explicitly with `absent = true`; removing it from the configuration relinquishes ownership and preserves it. Destroy forgets the entire resource and leaves router settings intact. Protect production configurations with `prevent_destroy`.

Existing firewall rules retain their placement relative to unmanaged rules. To change order or restore a missing rule at a specific location, configure `position` for every managed firewall rule using absolute package indices. Refresh observes those indices. Without positions, an update requiring a different managed order is rejected before staging; new rules otherwise append. Explicit placement is part of the Terraform configuration and must preserve the intended policy relative to unmanaged rules. Anonymous sections missing their unique match are recreated as named sections with deterministic provider-generated names and their declared match options.


## Rotate Wi-Fi keys

Use the sensitive write-only map `wireless_keys_wo`, keyed by managed named `wifi-iface` sections. Obtain values from ephemeral input variables and increase the positive `wireless_keys_version` when rotating. Keys are evaluated on creation and version changes; identical keys do not cause a router reload. They never enter saved plan or state artifacts. Omitting the map preserves existing keys. Refresh cannot detect key drift. A missing Wi-Fi section is never recreated without an explicitly supplied key. Increase the generation and supply the missing named section’s key to restore it; other missing members do not reset the generation.

The supported option allowlist covers network interfaces and bridges, WPA AP settings, DHCP pools and reservations, dnsmasq upstreams, firewall zones/forwardings/rules, the stock DNS selector, and Ethernet port mapping. Credentials are accepted only through `wireless_keys_wo`. See HashiCorp's [write-only argument contract](https://developer.hashicorp.com/terraform/plugin/framework/resources/write-only-arguments).

## Apply and recover

Before activation, the snapshot and boot service are synchronized to persistent storage. Cancellation before request execution only removes the unused preparation and never reloads or restores settings. Readiness is tied to the current boot, so an unexpected reboot cannot reuse stale confirmation eligibility. Completed transactions are atomically retired before their files are removed, and the boot service resumes interrupted cleanup.

Changes take a private snapshot of all six supported packages on the router and arm a 300-second watchdog before staging or committing. Uncommitted UCI changes, a pending transaction, conflicting AdGuard DNS ownership, or unsupported hardware stop the operation. Configuration is staged and checked with `fw3` before the package commits. The watchdog restores all six files if the provider does not confirm the change. Confirmation and recovery publish an atomic persistent decision. An interrupted restore resumes after reboot, and failed service restoration retains the snapshot and retries. Uncertain worker startup keeps its snapshot and service for inspection or recovery after reboot; no request is activated until the worker is armed. A single router worker owns cleanup. The winning decision is synchronized before restoration or cleanup. Confirmation only publishes the decision and waits for a transaction-specific durable confirmed outcome after that worker removes the snapshot, service and locks; ordinary refresh and adoption reject a transaction until cleanup finishes.

Network, Ethernet port-mapping, and wireless topology changes reboot the router. Existing AP setting and key changes reload Wi-Fi. A temporary init service restarts recovery after a reboot, including an unexpected reboot. Confirmed changes cancel recovery and remove the snapshot and service. The provider checks saved settings, managed rule order, SSH reconnection, declared active interfaces, selected wireless bridges, and the DNS process. Test client connectivity and the actual security policy independently after applying. The same router worker serializes staging, all commits, service reloads, restoration, and cleanup. The SSH process only prepares and activates this worker. The confirmation window is 300 seconds after reload or boot. A hung native UCI or firmware command can delay restoration; the snapshot and persistent service remain, and a router reboot resumes recovery.

Small nonsecret terminal-outcome records remain in `/root/.terraform-provider-glinet-results` so confirmation can be retried after a lost SSH response or reboot. Rollback and cancellation outcomes never acknowledge a successful apply. A provider error can mean recovery or confirmed cleanup is still pending; inspect the outcome and connectivity before retrying.

The transaction directory is `/root/.terraform-provider-glinet-configuration` on the router. Recovery does not restore credentials or data outside the six configuration packages. Power loss during file restoration, filesystem failure, or concurrent out-of-band writes require operator inspection and the external backup. Never bypass a host-key mismatch, remove a pending transaction, or reapply blindly after a failed confirmation.
